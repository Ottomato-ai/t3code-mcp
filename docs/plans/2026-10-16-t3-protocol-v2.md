The web client's own command builders (`client/assets/runtime-*.js`, `EnvironmentCommands.*`) and T3's built-in MCP were used as the reference for each mapping.

## Design

Keep every tool's output shape. Adapt at the client boundary.

1. **Header.** `T3Client.req` sends `x-t3-orchestration-protocol: 2` on every call.
2. **Read mapping (`src/v2.ts`, pure functions).** `client.shell()` and `client.thread()` detect V2 payloads and map them to the existing `ShellSnapshot` / `ThreadDetailSnapshot` shapes, so `attentionOf`, `threadRow`, `pendingRequests` and the launch desk keep working. Legacy payloads pass through unchanged.
   - Run status to turn state: `preparing|queued|starting|running|waiting` -> `running`, `completed` -> `completed`, `interrupted|cancelled|rolled_back` -> `interrupted`, `failed` -> `error`.
   - Pending request: `pendingRuntimeRequest.kind` `user_input` -> `hasPendingUserInput`, any other kind -> `hasPendingApprovals`.
   - Session in the shell (no session data exists there): active run or pending request -> `running`/`starting`; latest run `failed` -> `error`; latest run ended less than 30 minutes ago -> `ready` (T3 releases an idle provider session after `DEFAULT_IDLE_TIMEOUT_MS` = 30 min); older -> `stopped`; never ran -> no session. This feeds the launch desk cap.
   - Session in thread detail: real `projection.providerSessions` status (`waiting` -> `running`); no session left (detached) -> `stopped` when the thread has runs.
   - Activities for `pendingRequests` and the activity overview: synthesized from `turnItems` (`approval_request`, `user_input_request`, `command_execution`, `file_change`, searches, `dynamic_tool`, `error`) and resolved by `runtimeRequests` status.
   - `turnLimit` and `beforeCursor` are applied client-side over `projection.messages` (a turn starts at a user message). The cursor is opaque: `m:<messageId>`.
3. **Archived threads.** `client.shell({ includeArchived: true })` adds the RPC archived snapshot. Used by `list_threads` with `includeArchived` and by `search_threads`.
4. **Dispatch (`src/rpc.ts`).** One short WebSocket per dispatch, one `Request` frame, wait for its `Exit`. A failure before the socket opens with `ECONNREFUSED` keeps `notSent: true` for the launch desk.
5. **Commands (`src/v2.ts` builders, used by the tools).**
   - `send_message`: optional `thread.runtime-mode.set` / `thread.interaction-mode.set` when the override differs, then `message.dispatch` with `dispatchMode: start_immediately` (the server queues it behind an active run).
   - `create_thread`: `thread.create` then `message.dispatch` (same two-step flow as T3's built-in MCP), `createdBy: "user"`, `creationSource: "mcp"`.
   - `interrupt_thread`: `run.interrupt` on the active run; a clear error when nothing runs.
   - `stop_thread`: `provider-session.detach` for each provider session (the web client's `stopThreadSession`).
   - `respond_to_approval` / `respond_to_user_input`: `runtime-request.respond`.
   - `set_thread_title`: `thread.metadata.update`.
