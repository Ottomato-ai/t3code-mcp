# Zod audit fix (GHSA-mrhx-c7xc-m3w5): plan

**Goal:** `pnpm audit` / `npm audit` report no high finding for t3code-mcp, without breaking the MCP SDK or changing any tool's input schema on the wire.

**Tech stack:** TypeScript 5.9 (`tsc` to `dist/`), `node --test`, pnpm lockfile, `@modelcontextprotocol/sdk` 1.32.1.

## Facts

### The advisory

- GHSA-mrhx-c7xc-m3w5 (CVE-2023-54404), high, CVSS 7.5, CWE-770. Source: `gh api advisories/GHSA-mrhx-c7xc-m3w5` (the GitHub advisory database record behind https://github.com/advisories/GHSA-mrhx-c7xc-m3w5).
- Affected: `zod < 4.6.6`. First patched: **4.6.6** (published 2026-10-11). There is **no patched 3.x release**.
- Flaw: `$ZodArray` parse (`handleArrayResult`) walks every element and keeps one issue per failing element before any `.max()`/`.length()` bound is reported, so an oversized array exhausts memory.
- Fix: colinhacks/zod#6652, commit a0ebf970 "fix(v4): check array, set and map size bounds before parsing elements". It changes only `packages/zod/src/v4/core` (`schemas.ts`, `compile.ts`, `util.ts`). The legacy `zod/v3` code is not changed.

### Does t3code-mcp reach the flawed path?

- **Own tool schemas: no.** The 26 tools use only `z.string`, `z.number().int()`, `z.boolean`, `z.enum`, and one `z.record(z.string(), z.unknown())`. No `z.array`, `z.set` or `z.map`.
- **Through the SDK: yes.** The SDK's protocol schemas (`dist/esm/types.js`, 33 `z.array` calls) import `zod/v4`. With zod 3.25.76 installed, `zod/v4` is the pre-fix v4 core (`node_modules/zod/v4/core/schemas.js:622`, `$ZodArray` with `handleArrayResult`). Every incoming JSON-RPC message is parsed with it: from the stdio client, and in `--http` mode from any client holding the bearer token.
- Practical exposure is low (local stdio client; HTTP behind a bearer token), but the package is in the vulnerable range and the SDK path is real.

### Second high finding found by the audit

- GHSA-27r3-jxmh-p828, `body-parser >=2.0.0 <2.4.0`, via `@modelcontextprotocol/sdk > express > body-parser` (locked at 2.3.0). Patched: 2.4.0 (published 2026-10-22), inside express 5.3.0's `^2.3.0` range.
- Not reached: `src/http.ts` uses `node:http` and its own `readBody`, never express. Fixed anyway because the gate is "no high finding", and the fix is a lockfile-only bump inside an existing range.

### SDK compatibility

- `@modelcontextprotocol/sdk@1.32.1` declares `zod: "^3.25 || ^4.0"` as both a dependency and a peer dependency. zod 4.6.x is in range: no forced peer.
- The SDK detects v3 vs v4 schemas (`server/zod-compat.js`) and serializes v4 schemas with `zod/v4-mini`'s `toJSONSchema`, v3 schemas with `zod-to-json-schema`. So the serialized `inputSchema` can change if our schemas move to v4.

### Zod 4 migration guide (https://zod.dev/v4/changelog, https://zod.dev/v4/versioning)

- In zod 4.x the package root `"zod"` exports Zod 4; `"zod/v3"` keeps Zod 3; `"zod/v4"` stays forever.
- Relevant breaks for our calls: `z.number().int()` rejects unsafe integers (all our ints have `.max()` of 4000 or less, so no change); `z.number()` rejects Infinity (our ints are bounded); `z.record` needs two arguments (we already pass two); `z.unknown()` keys in an object shape become required at parse time from 4.4 (ours is a record value, not a shape key). `.describe`, `.optional`, `.min`, `.max`, `z.enum` are unchanged.

## Options

| Option | Clears audit | Fixes the SDK path | Tool schemas on the wire | Code change |
|---|---|---|---|---|
| A. `zod ^4.6.6`, keep `import { z } from "zod"` (Zod 4 classic) | yes | yes | may change (v4 serializer) | package.json + lockfile |
| B. `zod ^4.6.6`, import `"zod/v3"` | yes | yes (SDK uses `zod/v4`) | identical (same v3 serializer) | 5 import lines too |
| C. Stay on zod 3 | no (no patched 3.x) | no | — | — |

Decision rule: take A if the `tools/list` diff against main's build is empty; else take B, which keeps the wire output identical. In both, the SDK's protocol parsing runs on the patched v4 core. B leaves our own schemas on the legacy v3 code, which has no array/set/map schema, so it does not reach the flaw either.

## Decision (after step 4)

**Option B.** Option A was built and diffed first: same 26 tools, but 23 semantic changes on the wire. 22 tools lose `"additionalProperties": false` (the v4 serializer omits it for default objects), and `respond_to_user_input.answers` gains `"propertyNames": {"type": "string"}`. That changes what clients may send, so A is not the smallest change. Option B gives a byte-identical `tools/list` (same sha256 as main's build) and identical validation errors for invalid inputs. A guard test keeps array, set and map schemas out of the `zod/v3` files, because the legacy v3 code did not get the fix. Moving the tools to Zod 4 classic is a separate change that must decide the `additionalProperties` contract on purpose (for example with `z.strictObject`).
